## Introduction

A database write and the event that announces it to the rest of the system are two separate things. Committing a transaction and publishing a message are different operations, against different systems, and nothing forces them to succeed or fail together — unless something is specifically built to make that true.

Most of the time this doesn't matter. When it does — when something downstream genuinely needs to know that a change happened — the gap between "the write committed" and "the message went out" is exactly where real systems quietly lose events.

## The Problem

Publish an event right after a commit, as a separate step, and there's a window between the two: the transaction can commit and the publish can fail (a crash, a network blip, a dead broker), leaving a change that happened with nobody downstream ever told about it. Or the ordering can run the other way — a publish that appears to succeed just before a transaction that then rolls back, announcing something that never actually happened. Neither failure is exotic. Both are just "two independent operations, no shared outcome," which is what any two separate steps are by default.

## The Core Concept

The fix is to stop treating the write and the announcement as two operations. Write the event into a table in the **same database transaction** as the change it describes. Now there is only one operation, with one outcome: either both the change and the record of the event exist, or neither does — the database's own atomicity guarantee, which already exists for exactly this reason, is doing the work. A separate process then reads that table on its own schedule and actually delivers the event, decoupled from the original request. The event might be delivered a little later than the write happened, but it is _never_ delivered without the write having happened, and the write is never made without the event eventually being deliverable.

## Visual Model

```
WITHOUT AN OUTBOX                      WITH AN OUTBOX

1. COMMIT the change                   1. BEGIN transaction
2. publish() ── separate call             - write the change
   (can fail independently)               - write the event row
                                        2. COMMIT (both or neither)
   gap: change committed,              3. a separate process reads
   publish never happens                  unsent event rows and
                                           delivers them, later
```

The left side has a real gap between step 1 and step 2 — anything can happen in between. The right side has no such gap: steps 1 and 2 are the same commit. What happens after that commit (step 3) is a delivery concern, not a correctness concern — losing time there is recoverable; losing the fact that something happened at all is not.

## Implementation

The general shape needs only two things: an outbox table written in the same transaction as the business change, and a separate reader that picks up unsent rows and delivers them, marking each one handled once delivery succeeds.

```sql
-- Illustrative only — a generic shape, not a specific project's documented schema.
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 42;
  INSERT INTO outbox_events (event_type, payload, sent_at)
    VALUES ('funds_debited', '{"account_id": 42, "amount": 100}', NULL);
COMMIT;

-- Later, a separate process:
SELECT * FROM outbox_events WHERE sent_at IS NULL ORDER BY id;
-- deliver each one, then mark it sent
```

A real system documented in this portfolio, VaultPay, follows exactly this shape: its own `outbox_events` table sits alongside its `ledger_entries` table, and the ledger already writes to it as part of the same transaction that records a money movement — VaultPay's own case study is explicit that publishing to a queue directly from the request handler was considered and rejected, specifically because a queue publish failing outside the database transaction would leave a real money movement with nobody downstream ever hearing about it, or the reverse.

**What that case study documents, and what it doesn't**: the transactional write into the outbox table is stated as already how the system works. The downstream half of the picture — a relay process reading that table and delivering through a message broker to webhook and notification consumers — is documented as a later phase of the project's own roadmap, not yet reached. The pattern's own core guarantee (the write and the event either both happen or neither does) doesn't depend on which broker eventually reads the outbox, or how often — that detail is a delivery-mechanism choice, made separately from, and after, the correctness guarantee itself.

## Trade-offs

**Advantages**

- The event's existence is exactly as durable as the change it describes — no separate failure mode where one happens without the other.
- The guarantee comes from the database's own transaction boundary, not from careful sequencing in application code that has to be gotten right on every code path, forever.

**Disadvantages**

- Delivery is no longer immediate — a downstream consumer sees the event after a separate process picks it up and sends it, not the instant the transaction commits.
- There's a second table and a second process to build and operate, where "just publish after the commit" looked like one line of code.

**Alternatives**

- Publishing to a queue directly from the request handler, immediately after the write — the alternative actually considered and rejected in the real system this article draws from, precisely because it reopens the gap the outbox exists to close.

**When not to use it**

Not every write needs an announcement at all, and not every announcement needs this guarantee — if losing an occasional notification is genuinely a shrug rather than a real cost, a direct publish is simpler and the gap it leaves is one you've decided not to pay to close.

## Common Mistakes

**Treating "publish right after the commit" as basically the same thing as "publish as part of the commit."** They fail differently: the first has a real window where the two can disagree; the second, by construction, does not.

**Forgetting that the delivery side needs its own safety net.** A relay process that retries a delivery it isn't sure succeeded can send the same event more than once — which means whatever consumes these events downstream has to treat a duplicate delivery as harmless, a separate guarantee from the one this pattern itself provides. (See [Idempotency](/knowledge/idempotency) for that half of the problem.)

## Real-world Examples

VaultPay's own wallet ledger uses this pattern for exactly the reason described above: a payment or payout is real money moving, and the case study is explicit that the cost of a silently-lost downstream notification about it is not acceptable. Its `outbox_events` table is written in the same transaction as the `ledger_entries` row it describes — the transactional guarantee this article is about. The broker and worker layer that will eventually read that table and deliver to webhooks and notifications is real in the sense of being designed and decided, not yet in the sense of being the system's current, running behavior — an honest distinction worth keeping rather than glossing over.

## Key Takeaways

- A write and the event announcing it are two different operations by default — nothing keeps them in sync unless something specifically does.
- Writing the event into a table inside the same transaction as the change turns "two operations that might disagree" into one operation with one outcome.
- Delivery — a separate process reading the outbox and actually sending — is a different concern from the correctness guarantee itself, and can lag without breaking it.
- A system built this way still needs its downstream consumers to handle duplicate delivery safely; the outbox guarantees the event exists, not that it arrives exactly once.
